## 0. 阅读约定与产品边界

**一句话定位：**以虚构公司 LBB 的职场冲突为题材，让远程控场的 RajerWei 与近身压制的 JU GUAI 在经典像素街机规则下对战；笑点来自招式演出，胜负来自距离、读招、执行与能量管理。

本文所有人物背景、称号与评价均为**虚构游戏角色设定**，不作为对参考照片人物的现实评价。

| 标记 | 含义 | 优先级 |
| --- | --- | --- |
| U：用户已确认 | 本次对话确认的范围、角色、技能概念与汉堡 20% 效果 | 最高；调整前需重新确认 |
| D：首轮设计参数 | 为原型补齐的规则、数值、操作、视觉与技术方案 | 可通过试玩修订，修改时同步两份文档 |
| R：资料事实 | 当前工程或官方文档可核对的事实 | 附来源，不代表功能已经实现 |

**全文除显式标为 U／R 的内容，均为 D。**表内每项数值都有初始值；“首轮”表示可调，不表示由开发者临场猜测。平衡性、服务器容量和联机质量均须实测。

### 0.1 已锁定范围（U）

- 当前 Godot 项目全新设计；首发 macOS、仅键盘。
- 经典 2D 像素街机；传统轻重拳脚、方向指令、MAX 爆气与取消体系。
- 两名角色自由选择，允许镜像；1 对 1、99 秒、三局两胜。
- 单机对 CPU，以及无需账号的互联网好友房间码对战。
- 一张 LBB 办公室舞台；角色保留参考图的面部、发型、体型与日常服装。
- 本次产物是 GDD、视觉圣经和六张概念图板。

首版游戏范围不含手柄、触屏、其他桌面平台、本地双人、排位、账号、观战、聊天、剧情战役、独立训练模式、装备或付费系统。出招表与 CPU 简单档承担初次学习入口。

### 0.2 成功标准

1. 看得清：常态、攻击起手、防御、受击、投技和 MAX 具有不同轮廓与反馈。
2. 玩得懂：每个高收益招式都有明确成本或破绽，两位角色的赢法不同。
3. 梗完整：八个技能及两种专属受击动作全部出现，照片辨识点贯穿全部姿势。
4. 能对战：CPU 不读取玩家未来输入；联机双方在相同输入历史下得到相同战斗结果。
5. 便于实现：战斗参数、动画时序、资源归属和异常状态都有书面约定。

## 2. 对局与输入

### 2.1 对局状态

`菜单 → 选人 → 对局载入 → 登场 → ROUND / FIGHT → 战斗 → 回合结算 → 下一局或胜利页`

| 项目 | 初始规则 |
| --- | --- |
| 胜利条件 | 先取得 2 个回合胜利；生命降至 0 或时间归零判回合 |
| 生命／能量 | 双方最大生命 1000；能量 0–300，100 点为一格 |
| 时间 | 5940 个可运行战斗帧；HUD 显示剩余帧数除以 60 向上取整 |
| 回合开始 | 生命全满；首局能量为 0，之后保留上一局剩余能量；MAX、食物、飞行道具、连段记录全部清空 |
| 出生 | 玩家槽位 1 在 x=160 面向右，槽位 2 在 x=480 面向左，脚底 y=292 |
| 登场／回合提示 | 对局首局登场 120 帧；每局 ROUND 60 帧、FIGHT 30 帧；均不可行动 |
| 暂停计时 | 登场、回合结算、命中定格、超必杀停顿和抓取演出均不扣 99 秒计时 |
| 时间归零 | 先完成该战斗帧的伤害与合法拾取，再比较生命；生命高者胜 |
| 同帧双 KO／同血超时 | 双方均不加胜局，清场重开该回合，生命全满、双方能量归 0；第三次连续平局结束整场并显示 DRAW |
| 结算 | KO／TIME OVER 提示 90 帧，回合结果 90 帧；达到两胜后进入胜利页 |
| 镜像配色 | 槽位 1 使用基础色；同角色时槽位 2 强制备用色；换边不换配色或控制权 |

判断胜负只使用已确认战斗帧。联机预测到 KO 时可显示受击反馈，正式 KO 文字、胜局增加与胜利页必须等该帧输入确认。

### 2.2 键盘与格斗记号

数字方向相对**角色当前朝向**：5 中立，6 前，4 后，2 下，8 上。必杀只用正方向，例：26 为依次按下、前，无需斜方向。字母 A／B／C／D 是格斗动作记号，不是键盘字母。

| 动作 | 默认键盘 | 规则 |
| --- | --- | --- |
| 上／左／下／右 | W／A／S／D | 游戏按物理键位读取；不受输入法候选文字影响 |
| 轻拳 A／轻脚 B | J／K | 站、蹲、空中分别取对应普通攻击 |
| 重拳 C／重脚 D | U／I | 同上 |
| 翻滚 A+B | 空格，也可 J+K | 默认向前；按后方向时向后 |
| MAX B+C | O，也可 K+U | 普通启动或接触后快速启动，详见 §4 |
| 普通投 | 近身 4 或 6＋C | 条件不成立则出 5C；4 为背投、6 为前投 |
| 菜单确认／返回 | Enter／Esc | 菜单同时支持方向键和 WASD |
| 出招表 | 暂停菜单或选人页的“出招表” | 不增加战斗快捷技能键 |

游戏内改键覆盖方向、四攻击、翻滚宏与 MAX 宏。绑定冲突时交换旧绑定；不接受 Cmd、Option、Ctrl、功能键或系统组合键。支持恢复默认；音量与键位存入 `user://settings.cfg`。未冲突的设置应原样保留。

### 2.3 指令判定

- 同时左右为中立，同时上下为中立，攻击边沿仍有效。格斗输入与菜单输入分开消费。
- 每个方向序列总窗口 20 帧，超必杀 2626 为 30 帧；相邻必要方向最大间隔 8 帧，允许中立间隔并忽略按键交叠产生的斜方向，不允许相反的正方向插入；无需按住末方向超过 1 帧。
- 方向在采样时转成朝向相对值；角色自动换边时清空未完成的方向序列，已识别指令保留 5 帧输入缓冲。
- 组合键允许相差 2 帧。首个单键延后最多 2 帧确定是否构成组合；专用宏无此额外等待。
- 判定优先级：超必杀指令 → 必杀指令 → MAX → 翻滚 → 普通投 → 普通攻击。多攻击同时按下且不构成已定义组合时，D > C > B > A。
- 指令被消费后，同一攻击边沿不能重复触发。保留最近 30 帧方向历史，动作缓冲 5 帧；定格期间缓冲寿命冻结，只保留最新一个合法动作。
- 不能在受击、倒地或抓取演出中提前排队无限招式；起身／硬直结束前最后 5 帧可缓冲一次合法动作。

## 3. 基础战斗规则

### 3.1 空间、运动与判定盒

逻辑画布 640×360，战斗横向边界 x=16…624，地面 y=292，镜头固定。所有表内坐标均为逻辑像素；内部以 **1/256 像素整数**保存位置、速度和加速度。禁止把图片透明边界或渲染缩放当作碰撞盒。

| 参数 | RajerWei | JU GUAI |
| --- | --- | --- |
| 前走／后走，像素/帧 | 2.75／2.25 | 2.25／1.75 |
| 跑动，像素/帧 | 4.5 | 4.0 |
| 后撤步 | 4 输入两次，20 帧内成立；24 帧走完 64 像素，无无敌 | 同左，位移 56 像素 |
| 站立推挤盒 | x=[-18,18]，y=[-140,0] | x=[-24,24]，y=[-136,0] |
| 站立／空中受击盒 | x=[-15,15]，y=[-142,-6] | x=[-23,23]，y=[-138,-6] |
| 蹲姿受击盒 | x=[-18,18]，y=[-88,-6] | x=[-25,25]，y=[-92,-6] |

盒坐标以角色脚底为原点；攻击表 x 正值表示前方，y 负值表示脚底以上。朝左时镜像 x。移动后先限制推挤盒不出边界，再按重叠宽度平均推开两人；奇数固定点余数归槽位 2，墙边无法分摊的位移转给另一人。

空中跨过对手不被地面推挤阻止，落地恢复推挤。动作期间朝向锁定；站走蹲跑和落地恢复后自动面对对手。横坐标相同沿用上一朝向。

20 帧内完成两次前方向按下（中间需释放）进入跑动，持续按前保持跑；松开转站，按后转站防，按下转蹲，按上转大跳，攻击可从跑动直接启动。后撤步全程 24 帧不能出招或防御，可被打击和抓取。所有矩形采用半开区间，边缘仅相切不算接触。

### 3.2 跳跃与地面防守

| 动作 | 启动与运动 | 攻防限制 |
| --- | --- | --- |
| 小跳 | 上方向按下即进入 4 帧预备；4 帧内释放上，起跳初速度 -1280 固定点/帧 | 空中可做一次普通攻击，无空中防御；小跳不是无敌 |
| 普通跳 | 预备结束时仍按上，初速度 -1664 | 同上 |
| 大跳 | 跑动中起跳，或 2→8 在 12 帧内完成；5 帧预备，初速度 -1984 | 同上；横向速度使用跑速 |
| 空中运动 | 重力 +96 固定点/帧²；先 y+=vy，再 vy+=96；普通／小跳前后速度分别为前走／后走速度，中立起跳vx=0，起跳时锁定 | 不允许二段跳、空中必杀、空中变向；落地收招 4 帧 |
| 站防 | 地面按后，且处于站走蹲跑、可防御的起身自由帧 | 防“通用”和“中段”，不能防“低段”和抓取 |
| 蹲防 | 按下后 | 防“通用”和“低段”，不能防“中段”和抓取 |
| 翻滚 | 4 帧起手＋12 帧无敌移动＋14 帧收招，共 30 帧；总位移 80 像素 | f4–15 仅免疫打击和飞行道具，可穿人；抓取始终有效，起手收招可被打 |

翻滚不耗能量，只能在地面自由状态启动；不能取消攻击、硬直、倒地。翻滚内不拾取食物、不出招、不防御；全程贴地。首版没有防御取消翻滚、破防槽、蓄力模式或额外受身键。

### 3.3 帧、命中与状态

- 帧从 **f0** 开始；S/A/R 为起手、有效、收招帧数。首个有效帧是 fS，最后有效帧是 f(S+A−1)，恢复自由从 f(S+A+R) 开始。
- 普通打击同一次动作对同一受击者最多结算一次。多段招按子段 ID 分别结算；防住也会消费该段的命中资格。
- 硬直 H／B 为接触帧之后仍不可行动的战斗帧数，不包含双方命中定格；表内是完整值。防御优势可由 `B − (剩余有效帧＋R)` 算出，不把定格重复加入。
- 轻普通攻击命中／防御定格 5／3 帧，重攻击 8／5，普通必杀 7／4；召唤落地 10／6；文档大招每波 3／2。取同帧最大值，不相加。定格冻结整个战斗世界，网络帧仍运行。
- 普通攻击无削血。可防御必杀／超必杀削血为该段基础伤害的 10% 向下取整，削血不能把生命降到 1 以下。食物扣血、投技及命中伤害可以 KO。
- 硬直结束前不能插入防御；站走跑和蹲姿可立即开始防御。空中被普通打击击中进入空中受击，非浮空打击不重置vy，落地后软倒地；没有空中站防。
- 软倒地：落地后 24 帧倒地＋12 帧起身；硬倒地：36＋12。倒地与起身不可受击；起身结束后额外 8 帧免投，打击可命中。
- 默认非击倒打击击退受击者：轻 10、重 18、必杀 20 像素，在其硬直前 5 帧等分；防御时分别为 6／10／12。墙边剩余位移反推攻击者。全屏文件每波只推 4 像素，不反推远处施放者。
- 表中“浮空”使用 vy=-1536、vx=朝攻击方向 512 固定点/帧；落地软倒地。离地后最多接受 2 次成功打击；每段接触前目标已在空中才占一次预算，造成首次离地的打击不占预算。超出不再受击；预算在恢复地面自由状态后重置。

### 3.4 连段、同时命中与投技优先级

同一连段第 1／2／3…个成功命中动作的伤害倍率为 100%／90%／80%…，最低 40%，向下取整。一个多段动作只推进一次计数，各子段共用首次命中时的倍率。普通投、指令投、食物均不启动或延长连段；能接入连段的 P1-U1 使用该倍率。目标恢复一个自由战斗帧即结束连段。

每个战斗帧严格执行：

1. 读取双方输入、到期计时与有效动作；在同一旧状态上确定双方动作意图。
2. 移动、推挤、生成本帧攻击／道具，处理飞行道具相撞。
3. 从同一碰撞快照收集双方打击、防御与抓取候选。
4. 同时结算打击与削血，再判断抓取；因此双方有效打击可以相杀。
5. 打击优先于同帧抓取。攻击者受到成功打击或目标本帧 KO，则该抓取不成立。双方仅抓取互撞时：各退 24 像素、僵直 12 帧、无伤害。
6. 若已有 KO，跳过拾取；否则仅自由、未在本帧受击／防御／抓取的地面角色可拾取。
7. 应用计时减一、判 KO／超时，输出表现事件。

普通投可抓接地的目标，包括自由、防御姿势、翻滚、后撤步及地面攻击起手／收招；目标不能在命中硬直、防御硬直、跳跃预备、空中、倒地、起身、免投或共同演出中。同帧有效打击仍优先于抓取。受抓后 7 帧内按 C 或 D 可拆普通投；指令投和超必杀捕获不可拆。动作中没有自动霸体；未明确写无敌的帧均可受击。

## 4. 能量与 MAX

### 4.1 能量获得与花费

| 事件 | 攻击者获得 | 受击／防御者获得 |
| --- | --- | --- |
| 普通攻击命中 | 轻 +8，重 +12 | 每次动作 +6 |
| 普通攻击被防 | 轻 +4，重 +6 | 每次动作 +3 |
| 免费必杀命中／被防 | +10／+5 | +6／+3 |
| 普通投成功 | +10 | +6 |
| 花能量的必杀或超必杀 | 0 | 每次动作 +6／+3；不是每个子段加一次 |
| 挥空、食物恢复／扣血 | 0 | 0 |

MAX 内双方仍按表获得能量。花费在合法动作开始时扣除，受打断不退款；不满足资源或道具上限时不启动、不扣费，消费该技能指令并闪烁相应能量格 12 帧。

### 4.2 MAX 精确规则

| 项目 | 规则 |
| --- | --- |
| 普通启动 | 地面自由状态 B+C，花 100 能量；12 帧启动，可受击；完成后 MAX=600 个可运行战斗帧 |
| 快速启动 | 5C、5D 或 2C 成功命中后、原动作结束前输入 B+C；花 200；取消原动作，双方停顿 6 帧后 MAX=360 帧，施放者立即自由 |
| 不可启动时机 | 防御接触、空中、受击、倒地、投技／超必杀演出中；MAX 已激活时不能再次激活 |
| 普通取消 | 可取消普通攻击接触后转必杀或超必杀，详见动作表；无额外取消费用，目标招原本花费照付 |
| MAX 必杀互取消 | 已命中或被防的当前必杀，在原动作结束前转向许可表中的另一个必杀；扣 120 MAX 帧，剩余需严格大于 120；目标招原费用照付 |
| 许可表 | Rajer：P1-S1 ↔ P1-S3；JU：P2-S1 ↔ P2-S2。每条取消链每个必杀 ID 最多出现一次 |
| 不参与互取消 | 汉堡、强制加班、普通投、超必杀；不允许取消挥空或尚未接触的飞行道具动作 |
| MAX 超必杀 | MAX 有剩余时执行同一个 U1 指令，额外花 100 能量，立即清空 MAX；使用 U1 的强化伤害，其余输入与捕获条件不变 |
| 结束 | MAX 时间为 0、使用 MAX 超必杀、角色 KO 或回合结束；普通受击和倒地不直接清空 MAX，但可运行战斗帧仍扣时间 |
| 不附加的效果 | MAX 没有持续加攻、无敌或霸体；收益来自取消和强化超必杀 |

取消不重置目标硬直，也不重置连段倍率或浮空追击预算。同一次接触只能消费一个取消。旧招已经发出的飞行道具／召唤可继续存在，但未执行到的生成帧取消；同一条取消链记录进入新的必杀后立即更新，防止回滚期间重复扣费。

**MAX 学习示例：**JU GUAI 的 5C 命中 → 快速 MAX → 5A → P2-S2 → MAX 取消 P2-S1，是接触取消练习路径；能否形成全程真连需依距离、接触帧和后续实测确认，文档不把演示路径标为已验证连招。

| 成功拾取 | 一次修改生命并移除实体，生成一次拾取事件；嘴边两姿势吃东西反馈可叠在移动上，不另加控制锁定 |
| 镜像 | 每份食物独立记录 owner_slot；两名 RajerWei 不能把对方汉堡当自己的恢复，也不能吃对方披萨 |
| 同帧伤害与食物 | 打击先结算，KO 不可吃；受到硬直也不可吃；无伤害命中时才检查食物 |
| 暂停／定格／共同演出 | 普通世界、食物飞行／激活／寿命、MAX 和回合时间都冻结；共同演出仅推进自己的相位时钟 |
| 已提交召唤遇到共同演出 | 保存当前阶段并暂停，演出结束继续；没有额外生成披萨或重复落地命中 |
| 双方超必杀同帧启动 | 同一全局 12 帧停顿，仅停一次；资源各扣一次，结束后同时按各自起手推进 |
| 时间归零与捕获同帧 | 该帧打击先结算；若捕获成立且没有 KO，则完成已接受演出，再按演出后的生命判超时；不再接受新动作或食物 |
| KO 与持续攻击 | 普通战斗立刻锁输入、取消未来生成事件；保留本帧双方伤害；只允许已结算抓取的无伤害出口演出完成 |

运行中的共同演出全场只能有一个。按 §3.4 解决同帧候选后确定唯一持有者，严禁同时出现两个办公室道具场景或两个各自冻结对方的状态。

食物飞行统一使用整数抛物线插值：t=0…T，x=start_x+(end_x−start_x)×t/T；y=start_y+(end_y−start_y)×t/T−4×h×t×(T−t)/(T×T)，每次除法向零取整，全部位置先转为1/256像素整数。汉堡从施放者前方24、脚底上方96像素出发，T=20、h=24；披萨从召唤落点上方110像素出发，T=24、h=32。落点y均为292，t=T时固定落地，食物图像锚点贴地。

## 8. CPU、菜单与反馈

### 8.1 CPU

单机玩家自由选人；默认 CPU 为另一角色，选人页可切换为镜像。每局开始随机种子固定在对局记录中，CPU 决策通过同一输入接口提交，不直接写位置、状态或强制命中。

| 难度 | 观察延迟 | 决策间隔 | 符合条件时防御／反击选择率 | 行为限制 |
| --- | ---: | ---: | --- | --- |
| 简单 | 24 帧 | 18 帧 | 35%／20% | 最多两次普通攻击接一个必杀；不用快速 MAX |
| 普通 | 16 帧 | 12 帧 | 60%／45% | 使用投技、普通 MAX 与简单接触取消；主动争夺食物 |
| 困难 | 10 帧 | 8 帧 | 80%／65% | 使用快速 MAX、两次必杀取消、针对预警跳／滚；仍遵守实际指令输入时间 |

概率用来在**基于延迟观察已满足条件**的候选中选择，不代表攻击必定防住。CPU 只看延迟后的公开状态、距离和预警，不能读玩家当前输入缓存、随机未来或隐藏攻击盒。每次决策只确定一段最长 30 帧的方向／按钮序列；受击后按规则中断。

### 8.2 界面与设置

- 主菜单：单机对战、互联网对战、设置、出招表、退出。
- 单机选人：选择角色、CPU 角色、难度；确认后显示两人立绘和键位提示。
- 联机入口：创建房间、输入房间码。房间页显示代码、双方角色与配色、准备状态、连接质量；双方准备且资源载入完成后才开战。
- 胜利页：胜者、局分、再战、重新选人、返回菜单。单机立即响应；联机双方确认再战才开始，30 秒未确认则保持房间等待。
- 设置：主音量、音乐、音效分别 0–100，默认 80／60／80；窗口／全屏；震屏开关（默认开）；减少闪光（默认关）；键位与恢复默认。
- 单机 Esc 或失焦立即暂停，回焦不自动恢复；恢复前给 3 秒倒计时。联机 Esc 打开本地菜单，比赛继续，角色后续输入归中立；失焦同理，明确显示“对局仍在继续”。
- 所有菜单键盘可操作，焦点有描边和箭头；说明文字与选项均有足够对比度。房间码可粘贴，输入框过滤到允许字符并自动大写。

### 8.3 战斗反馈与声音方向

HUD 常驻：双方头像／显示名、生命条、剩余时间、两枚胜局标识、三格能量、MAX 余量；在线额外显示对手链路延迟估计与连接状态。连击提示在画面侧边，不遮角色。

声音采用短促街机鼓点与办公室键盘、打印机、盖章、纸张等音色。基础音乐四段：菜单、对战循环、最后 20 秒加速层、胜利。声音事件最小 24 项：菜单移动／确认／返回，轻击／重击／防御，挥拳／踢腿，跳／落地／翻滚，受击，能量就绪／MAX／大招停顿，八招各一类专属音效，拾取。回合、KO 用屏幕文字和通用音效，不要求真人语音或声音克隆。

同类声音每帧最多一次、同时最多四路；总体音量限制避免文档五波叠成尖锐噪声。联机效果事件按 §9 去重。

## 9. 技术与互联网对战契约

### 9.1 已知环境与方案

**R：**当前 `project.godot` 声明版本特征 4.7，使用 Forward Plus，目录尚无游戏场景或战斗代码。文档没有把这个配置等同于已验证的 Godot 安装版本。

客户端以 GDScript 实现，战斗模拟是与渲染分离的纯数据推进器，固定 60 网络 tick/s。2D 渲染使用 Compatibility；正式实施时核对编辑器与导出模板为同一 4.x 版本。关键信息同步用 ENet/UDP，服务端使用同版本 Godot headless。[Godot 官方网络说明](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html) · [无界面服务器导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_dedicated_servers.html)

服务器（U）：上海五区，4 核 CPU、4GB 内存、5Mbps 带宽，Ubuntu Server 24.04 LTS 64bit。主机只承担房间管理、输入转发和一致结果确认；每个客户端各自运行相同模拟。所有客户端直接连服务器，玩家不需要路由器端口映射。

首版不引入数据库、账号、第三方匹配服务或新增回滚插件。房间驻内存，服务器重启后房间结束；恢复服务后玩家重新创建房间。

### 9.2 房间生命周期

`连接 → 协议/规则版本检查 → 创建或加入 → 双方选人 → 双方准备 → 载入确认 → 输入起始屏障 → 对战 → 结果确认 → 房间/再战`

- 服务器监听 UDP 7000；地址配置在客户端发行配置中，实际公网 IP 在部署阶段填写，不要求现在提供登录凭据。
- 六位随机房间码，字符集 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`，碰撞则重取。每房两人，初始容量上限 **4 间房／8 个已入房玩家**，不是硬件容量承诺。
- 创建者为槽位 1，加入者为槽位 2；槽位在本场固定。开始前离开的空槽可以被新玩家加入；对战中不允许第三人接替。
- 房间空闲 10 分钟自动销毁；连接后 15 秒未入房断开。对局结束后房间中一人离开，保留者成为房主并重编号为槽位 1，清除准备状态；下一位加入者为槽位 2。重编号只能发生在房间状态，不能改写正在进行或已结束对局的操作者身份。
- 单次建房／加入请求每连接每秒最多 2 次；未入房连接全服最多 16 条，全部 ENet 连接上限 24。名称不接受任意富文本；显示对手为玩家 1／玩家 2＋角色名。
- 开战必须满足协议版本、规则版本、资源清单版本完全相同；不同则返回“版本不一致，请更新游戏”，禁止勉强开局。
- 服务器给出 match_id、slot_id、两角色、配色、随机种子与起始屏障。双方确认载入后，各自先上传 3 个中立输入帧；收到双方 READY_GO 后从模拟帧 0 开始。

### 9.3 最小接口与数据

这些是后续实现必须保持一致的**数据契约**，本次不创建运行时代码或网络库。

| 数据 | 必填字段与行为 |
| --- | --- |
| `FighterDefinition` | character_id、最大生命、移动常量、受击／推挤盒、move_id 列表、配色；角色静态数据只有一份 |
| `MoveDefinition` | move_id、指令、S/A/R、各有效段范围与盒、伤害、H/B、资源、取消许可、生成事件；§5–6 为值来源 |
| `InputFrame` | match_id、slot_id、frame:int32、buttons:uint16；位 0–3 为绝对上/下/左/右，位 4–7 为 A/B/C/D，位 8/9 为滚/MAX 宏，其余为 0 |
| `InputBatch` | 本连接槽位的当前帧及最近 7 帧输入、已收到对手的最高连续帧；同一帧按钮一经接受不得改写 |
| `BattleState` | 帧号、回合与胜局、剩余时间、两角色全部动态状态、能量/MAX、动作帧、方向历史与缓冲、连段与免投／追击计数、食物拾取间隔、实体列表、全局定格／演出、随机状态、实体计数器 |
| `BattleEntity` | entity_id、种类、owner_slot、出生帧、位置／速度、阶段／寿命、每目标每子段命中位、已提交生成事件；食物恢复量和归属不能从颜色推断 |
| `PresentationEvent` | 确定性 event_id=`match_id/frame/源实体/子事件`、类型、坐标、操作者；用于音效、粒子、镜头与文字去重 |
| `Result` | 已确认终局帧、胜者或平局、局分、该帧状态摘要；双方一致后服务器发正式结果 |

输入只允许连接发送自己的槽位，服务器从 sender 身份覆盖 slot_id；拒绝越界位、超长批次、旧 match_id 和离当前进度过远的帧（最多超前 120、落后 240）。批次必须递增排列，重复历史相同则忽略，不同则终止该场为输入冲突。

### 9.4 回滚、丢包与一致性

- 输入使用独立不可靠通道，60 批/秒，批内带最近 8 帧冗余；房间与载入／结果使用独立可靠通道，避免控制消息阻塞输入。
- 固定本地输入延迟 **3 帧**：准备推进模拟帧 n 时采样的输入作用于 n+3，n不是墙钟tick编号。远端缺失输入预测为其最后一帧按钮状态，边沿由逐帧变化推导；不会凭空重复按下攻击键。
- 保存最近 **20 个**完整模拟快照及 **240 帧**已采样输入。迟到输入与预测不同则恢复最早受影响帧之前的快照，重新推进；最多回滚 **12 帧**。
- 每个批次报告对手输入最高连续帧；发现缺口持续3个网络tick，或缺口将离开8帧冗余范围时，通过第三个独立可靠通道请求补发缺口，每批最多16帧，来自已保留历史。补发不得改写旧输入。超出240帧可恢复历史时以连接中断结束，不能凭预测越过永久缺口。
- 下一帧若需要预测超过 12 帧，双方各自在最后可推进点等待，显示“等待网络”；不自行丢帧或跳过伤害。收到历史后追赶；连续 5 秒不能推进则终止为“连接中断，本场无结果”。
- 等待期间网络继续重发／补发，但不递增模拟帧号或无限排队新战斗输入；恢复时读取最新按住状态继续采样。已采样的延迟输入不可撤回。已确认帧指双方均持有真实输入、且双方连续接收确认已覆盖该帧，不仅是本机收到一次数据。
- 定格和演出期间网络 tick 继续；世界时钟按 §7 冻结。输入解析、动作边沿与缓冲也在快照内，不能在回滚外用实时键盘状态重建过去。
- 碰撞使用显式整数矩形，模拟不调用浮点刚体物理、渲染节点变换或系统时钟。随机使用 xorshift32：`x ^= (x<<13)&0xffffffff; x ^= x>>17; x ^= (x<<5)&0xffffffff; x &= 0xffffffff`；种子不能为 0。
- 状态序列化为固定字段顺序、定长小端整数；动态实体按 entity_id 升序。每 60 个已确认模拟帧计算一次 CRC32，双方经服务器比较；明确失配后结束为“同步异常，本场无结果”，首版不从任一客户端强行覆盖另一方状态。
- 已播放短音效保留 event_id 去重记录，回滚重放不重复播放；错误预测的音效无法撤回，但不能再播一次。预测粒子随重建刷新；KO、胜局、胜利音乐只在确认后播放。
- 终局最多等 5 秒确认结果；摘要不一致或缺失即无结果，不能让双方各自记录胜利。重赛清空上一场事件去重集合和网络帧历史。

### 9.5 故障与服务部署

| 情况 | 用户看到的结果 |
| --- | --- |
| 服务无法连接／UDP 不通 | 8 秒超时，“无法连接服务器”，可重试或回菜单 |
| 错误、过期房间码 | “房间不存在或已结束”，留在输入页 |
| 房间已满／服务器满 | 分别明确提示，不修改现有房间 |
| 对手准备后换角色 | 清除双方准备状态，重新准备 |
| 战斗中主动退出 | 服务端收到可靠退出后向对手显示“对手已退出”；本场标记退出终止，不计正常胜局 |
| 掉线或服务器重启 | 最多 5 秒等待后无结果结束；不由 CPU 接管，不支持中途续局 |
| Esc／失焦 | 本地菜单或提示；比赛继续，后续输入中立，不把过去已发送的 3 帧输入撤回 |
| 规则或状态失配 | 拒绝开局或结束当前场；显示清楚原因并回房间／入口 |

部署初值：导出 Linux x86_64 headless 包，以专用非 root 用户运行；用 systemd 单进程守护（异常退出 3 秒后重启），放行 UDP 7000。代码不保存 SSH 密钥或服务器管理密码。仅记录连接数、房间数、流量、延迟、等待次数、失步和退出原因；日志按日轮换保留 7 天，不保存聊天或私人资料。

**带宽预算是估算：**按含协议开销每次单向转发 160 字节、每玩家 60 次/秒、每场两个玩家估算，服务端出站约 `160×60×2×8=153,600 bit/s≈0.154Mbps`。4 场约 0.615Mbps，预留两倍至约 1.23Mbps；上行入站同量级。实际序列化包大小、可靠消息和重发必须抓包测量，5Mbps 不自动保证任何延迟或并发数量。

客户端 HUD “延迟”显示两端到服务器 RTT 之和作为端到端往返估计，每秒更新，不冒称为直接测得的 P2P RTT。4 房间初始上限仅在压测后提高。
